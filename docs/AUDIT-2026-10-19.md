# Audit — 2026-10-19

Scope: `app.py`, `scripts/predict-sunset.py`, deploy config (`vercel.json`, `pyproject.toml`),
contract docs (`README.md`, `SKILL.md`, `references/`). No third-party deps (project is
zero-dependency by design); all fixes are stdlib-only code changes.

## Findings

| ID | Sev | Area | Finding | Status |
|----|-----|------|---------|--------|
| F1 | P1 | engine | Any `--date` other than today silently uses **tomorrow's** forecast | fixed |
| F2 | P1 | engine | `sunrise` predictions sample the 16:00–19:00 (sunset) window | fixed |
| F3 | P1 | engine | Legitimate `0` values (e.g. 0% cloud) are dropped as missing | fixed |
| F4 | P1 | api | `/api/predict?lat=abc` raises uncaught `ValueError` → 500 traceback | fixed |
| F5 | P2 | engine | Sunsethue 200 response with missing `data.quality` fabricates a `0.5` prediction and pushes it | fixed |
| F6 | P2 | engine | Unknown explicit location silently predicts for 杭州 | fixed |
| F7 | P2 | api | Bearer token compared with `==` (non-constant-time) | fixed |
| F8 | P3 | engine | Error text says "日落时段" even for sunrise | fixed |

### F1 — date → day_index collapse (P1)

`scripts/predict-sunset.py:812`: `day_index = 0 if date_str == today_str else 1`. Every
date that is not literally today — past dates, `+2d`, `+30d`, even garbage strings — is
mapped to tomorrow's slice of the 3-day Open-Meteo response and reported under the
requested date. README advertises `--date 2026-05-13` for trip planning, so this is a
documented contract violation.

Fix: `_resolve_date()` strictly parses `YYYY-MM-DD`, rejects past dates and anything
beyond Open-Meteo's `forecast_days` window (`today .. today+2`), and returns the real
day index. `FORECAST_DAYS` constant is shared with `fetch_openmeteo()` so the window and
the fetch cannot drift.

### F2 — sunrise uses sunset hours (P1)

`scripts/predict-sunset.py:161,171`: `_hour_index_for_date` hardcodes `16 <= h <= 19`, so
`--type sunrise` (event hour ≈ 5–7) scores 16:00–19:00 cloud data as the sunrise
prediction. The error message (`:249`) also says "日落时段" (F8).

Fix: candidate window is event-relative, `[event_hour-2, event_hour+1]`. For a sunset at
18:00 this is exactly the old 16–19 window, so sunset behavior is preserved.

### F3 — zero values treated as missing (P1)

`scripts/predict-sunset.py:265,401-407`: `round(low_cloud, 0) if low_cloud else None` and
friends convert genuine `0` (clear-sky 0% cloud is the most common case) into `None`;
formatters then omit the value entirely, so a clear-sky report shows no cloud line at all.
The module's own `_v` helper documents the invariant "0 是有效值，None 才是缺失" — the
output dict violates it.

Fix: `is not None` checks throughout the output dict (and for `visibility`, where 0 m is
a real fog reading).

### F4 — unvalidated query input crashes the WSGI app (P1)

`app.py:148-149` runs `float(lat)`/`float(lng)` **outside** the handler's `try`; a
non-numeric value propagates out of `app()` → Vercel 500 with traceback. Related: the
reason-phrase map (`app.py:233-240`) has no `400` entry, so any future 400 response would
be sent as `"400 OK"`.

Fix: input validation gets one owner — the engine raises `ValueError` for bad coordinates,
bad dates, unknown locations, bad `event_type`; `app.py` maps `ValueError` → `400`,
anything else → `500`, upstream failures stay `502`. Reason map gains `400: "Bad Request"`.

### F5 — fabricated prediction on malformed Sunsethue response (P2)

`scripts/predict-sunset.py:817-819`: `result.get("data", {})` + `data.get("quality", 0.5)`
means a 200 response with an unexpected shape yields a made-up `quality: 0.5` that is
formatted and pushed as a real forecast.

Fix: require a numeric `data.quality`, else fall through to the Open-Meteo engine (the
established cascade). Quality is clamped to `[0, 1]` per the API contract.

### F6 — silent fallback to 杭州 (P2)

`scripts/predict-sunset.py:416-432`: `?location=Atlantis` (or a typo'd
`SUNSET_LOCATION`) silently produces a 杭州 prediction labeled "杭州".

Fix: unknown explicit `location`, unknown `SUNSET_LOCATION`, partial coordinates
(lat without lng), and out-of-range/nan coordinates raise `ValueError` (→ 400/exit 1).
The no-input default (杭州) is unchanged.

### F7 — timing-safe bearer compare (P2)

`app.py:64`: `hmac.compare_digest` replaces `==` for the `CRON_SECRET` check. No
behavior change; no test (a test would pin the implementation, not the contract — the
401/auth contract itself is unchanged).

## Design / defaults chosen

1. **Forecast window `today .. today+2` applies to all queries**, even when
   `SUNSETHUE_API_KEY` is set. Sunsethue alone might serve further-out dates, but one
   uniform limit matches the README disclaimer (">48h 预报不可靠") and keeps error
   behavior predictable. Revisit if Sunsethue becomes the primary engine.
2. **Bad input fails loudly** (400 / exit 1) instead of silently degrading; server-side
   misconfiguration (`SUNSET_LOCATION` unknown) also fails loudly instead of silently
   predicting 杭州.
3. **Error taxonomy**: `ValueError` = caller/input error → `400`; engine/upstream failure
   → `502` (unchanged); unexpected exception → `500`.
4. **Sunrise hour window** `[event-2h, event+1h]` — same sampling as before for sunsets,
   morning hours for sunrises; picks the hour closest to the event.
5. **Tests** use stdlib `unittest` (zero-dependency constraint), live in `tests/` (already
   excluded from the Vercel bundle by `vercel.json`), and target only the fixed contracts
   at their owning boundary. Run with `nice -n 19`.

## Addendum 2 — push auth default

- **`?push=1` now requires `CRON_SECRET`** (401 otherwise — including when the env
  var is unset). Previously a missing secret meant open push: anyone with the URL
  could trigger Server酱 pushes (quota drain / spam to the owner's WeChat).
  `/api/cron` is unchanged: bearer when `CRON_SECRET` is set, Vercel platform Cron
  (UA `vercel-cron`) still runs when it is not — secret-less deployments keep
  their daily push. `PushAuthTest` pins both sides of the gate.

## Addendum 3 — small robustness defaults

- `compute_sunset_quality`: when the event time is missing/unparseable, the
  fallback hour is now event-type aware (18 sunset / 6 sunrise) — a sunrise
  request no longer samples the evening window in that path.
- `resolve_location`: `location` and `SUNSET_LOCATION` are stripped before the
  map lookup (stray spaces/newlines from `.env` files no longer read as
  "unknown city"); the returned name is the stripped value.

## Addendum 4 — input normalization and JSON errors

- `_resolve_date` trims whitespace in `date`; `run_prediction` normalizes
  `event_type` (strip + lowercase) before validation — `" 2026-05-07 "`,
  `Sunrise` work; junk is still rejected. Consistent with the location
  stripping in Addendum 3.
- CLI `--json` now emits errors as `{"ok": false, "error": …}` JSON on stdout
  (exit 1) instead of `❌ text`, so machine consumers never parse human prose.
  Non-`--json` output is unchanged.

## Addendum 5 — confidence semantics

- `confidence` previously measured only data completeness, so a +2-day forecast
  printed `100% 🟢高` despite the README's own ">48h 不可靠" disclaimer. It now
  multiplies completeness by a lead-time decay (1.0 / 0.85 / 0.70 for day 0/1/2,
  chosen to match the stated 48h reliability horizon): +2d tops out at 0.70 and
  can never read 🟢高. Wording synced in README/SKILL.
- Parked (docs-only, next candidate): `references/locations.md` lists 大理 and 9
  international cities that `LOCATION_MAP` rejects, while the unknown-location
  error points users at that file. The engine's timezone is hardcoded
  `Asia/Shanghai`, so international cities must stay reference-only; the doc
  needs a "内置城市 vs 坐标参考" split and the "21 城" count claims need syncing.

## Addendum 6 — locations doc sync + timezone design note

Docs-only sync (no code): `references/locations.md` is now split into
**✅ 内置城市** (exactly `LOCATION_MAP`'s 21 names, all UTC+8) and **🧭 坐标参考**
(大理 + 9 international cities, usable only via `--lat/--lng`); README/SKILL
count claims now say "内置 21 城". The Addendum 5 parking item is resolved.

Why international cities stay out of `LOCATION_MAP` — design sketch for the
timezone support they need first:

1. Problem: map entries carry no timezone while the engine hardcodes
   `Asia/Shanghai` (`fetch_openmeteo` `timezone=`, `TZ_CST`, `_utc_to_cst`,
   `datetime.now(TZ_CST)`). For non-UTC+8 coordinates the event instants are
   right but every rendered time is a Shanghai-clock value — misleading output.
2. Design: `LOCATION_MAP: name -> (lat, lng, tz)` carrying IANA names (the
   reference table already has them); pass `timezone=tz` to Open-Meteo (IANA
   accepted); render with `zoneinfo.ZoneInfo(tz)` instead of `TZ_CST`;
   `_resolve_date`'s "today" and the report timestamp use the location tz;
   `_utc_to_cst` becomes `_utc_to_local(tz)` for Sunsethue magics; `--lat/--lng`
   callers need a `--tz`/query param (default `Asia/Shanghai`).
3. Scope: ~30-40 lines across engine + tests (tz-aware date window and
   rendering). Until then, non-UTC+8 coordinates stay reference-only and the
   doc states the Shanghai-clock caveat.

## Addendum 7 — engine-fallback transparency

- With `SUNSETHUE_API_KEY` set, engine-1 failures (HTTP error, timeout,
  malformed 200) fell back to Open-Meteo with zero signal — `source:
  "open-meteo"` alone cannot distinguish "key broken" from "key unused".
- `run_prediction` now adds an optional `engine_note` (only when engine 1 was
  attempted but not used): `engine1(sunsethue) failed: <err>; fell back to
  open-meteo` or `… returned no data.quality; …`. Forwarded verbatim by CLI
  `--json` and the HTTP API; message bodies unchanged (no push noise). Default
  chosen: free-form string, stable across error kinds; contains no secrets
  (errors are `str(exc)`, key travels in a header).
